# Idle Spiral OpenSpeedy runtime patch

Idle Spiral 3.0.82 build 117 (Unity/Mono x64), OpenSpeedy 3.3.8. Original game binaries remain unchanged. Installation and removal are documented in [使用說明](使用說明.md); evidence and limits are in [PERFORMANCE.md](PERFORMANCE.md).

The current version targets 100× actual simulation. DesignCountGuard caches the original pure six-argument visible-design count, comparing every array element and runtime/entitlement argument. Ownership queries still run. Broad parameter and recurrence caches are excluded.

HousekeepingGuard2 pauses analytics coroutines and stops the accelerated watchdog on the Unity main thread. Original Steam callbacks still execute on that thread, at most 20 real-time polls/second. At factors >=100, simulation permits up to 512 fixed 0.02-second steps with a cooperative 40 ms budget. Lower factors retain AdaptiveGuard's 8–16 ms budget. Step order, rewards, bounded debt and overflow handling remain intact. It also makes `PcFrameRateController` keep the saved frame rate when the window is unfocused, instead of the game's 20 FPS background cap.

AutomationGuard runs the four automation controllers on the OpenSpeedy clock and delivers battle `StateChanged` updates to `BattleUIManager` and `Battle_Mono` once per frame with the final state, so auto-start restarts (battle → quitting → battle within one step) no longer switch Doozy views each time. Outside season runs it also resets Daily Spiral tries once per 86400 extra game seconds from the factor, by clearing the stored reset date so the game's own `EnsureCurrentDay` writes the real date; the Daily panel's reset countdown shows the remaining game-day seconds. Theory auto study charges each `LevelUpByLevel` batch once (the original loop charges every level the starting level's cost, at about 7 µs per level), and above 1× takes every level the resources afford (1e15 safety cap), so Inspiration income is the only limit.

ClockIsolation uses the original OpenSpeedy shared factor and per-process controller flag, but redirects the verified native module's private enable-reader data pointer to a process-lifetime false byte. Native clocks, sleeps and waits therefore run at 1×. Managed elapsed admission applies the selected factor exactly once. It explicitly rewrites admission and factor call sites to avoid stale JIT inlining. No executable native bytes are patched; removal atomically restores the original pointer. Hash, export bytes and aligned slot checks reject unsupported binaries. The GUI checkbox and shared factor remain usable. speedpatch64 enables its host process when it loads, so AutoInstall calls `SP_Disable` for the game right after loading it (only when the autoloader loaded the DLL itself): a launch starts at 1× and follows the OpenSpeedy Speed switch from there. This changes all native timing in this game process, including cosmetic animation, not Steam's processes.

Steam startup uses official Doorstop 4.5.0 and a hidden .NET 8 helper. After at least two real seconds and the current process's initialization marker, the helper installs the bounded runtime and native DLL, immediately enables ClockIsolation, then installs DesignCountGuard → HousekeepingGuard2 → TheoryGuard → RenderGuard → AdaptiveGuard → AuthGuard → CalendarGuard → the idempotent original runtime loader. It exits after completion or a 90-second readiness timeout. No permanent service is added. This full chain was verified by an actual Steam relaunch on 2026-10-24.

RenderGuard suppresses the central spiral through the game's existing ownership API, preserving theta and achievement notifications. TheoryGuard shares two progress reads only within one theory update, preserving original EXP arithmetic. AuthGuard and CalendarGuard preserve real credential/calendar time and a real-time autosave interval. Eight original game/SDK hashes and the original bounded-runtime hash are checked.

Status files are snapshots. `isolation-status.txt` is authoritative for the managed factor and controller enable flag: the original runtime's `autoload-status.txt` may print `enabled=False` because its native clock reader is intentionally isolated. `housekeeping-status.txt` describes the effective high-speed budget and cap. Older adaptive/runtime files retain their baseline controller values, while their measured timing and backlog counters remain useful. A stale status file during a stall is not a live measurement.

Native dump unwinding localized historical long waits to SteamAPI_ManualDispatch_GetNextCallback, including ReadFile and condition-variable waits. A healthy 100× minute before clock isolation was followed by another stall. Clock isolation is a tested mitigation, not proof of Steam's root cause or permanent freeze elimination. New achievement unlock/upload and 200–500× long-term stability remain unverified. Raw dumps stay local.

Local verification includes exact design-count comparisons, bounded-budget tests, controller/clock isolation and restoration, full isolated autoload, official native bootstrap, transactional installer rollback, original hashes, actual Steam restart and live simulation/save measurements. See PERFORMANCE.md for final observations.
